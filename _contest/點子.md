- **一句話**：Handshake — 把 1960 年代的聲學數據機搬進瀏覽器，網路斷了也能讓兩支手機用「聲音」互傳文字（地震後基地台壅塞、沒訊號的地下室）（Resurrection）
- **抄了誰**：抄 Faxi「讓一種舊通訊技術復活，綁一個真實族群」的形狀，把傳真換成撥接數據機的嗶嗶聲。萬聖節的皮抄 Seance：介面是一場降靈會，兩支手機互相「通靈」，而那段聲音本身就是資料。
- **評分表怎麼拿分**：五項同為 20%，依這題最強到最弱排。Innovation：自己用 Web Audio 寫 FSK 調變，不靠網路也不用配對，多數評審沒看過。Presentation：影片裡關掉 Wi-Fi，「嗶」一聲字就傳過去，一眼就懂。Impact：2024 花蓮地震後通訊壅塞是真事，傳的是位置、短訊和緊急聯絡人。Tech：編碼／解碼的 round-trip 天生適合 property-based testing；hook 在改調變參數時自動跑 PBT 和錯誤率報表；spec 拆成調變層、協定層、UI 層；MCP 接 Context7 查 Web Audio。Design：克制的黑白降靈會排版配上波形，「靈」的清晰度就是訊號品質指示，陰森直接是功能。
- **AI 做不到的部分**：聲學通道只能實測。要借 15 支以上同學的不同手機，在教室、捷運、宿舍走廊量真實錯誤率，再依實測決定頻段、鮑率和錯誤更正。AI 沒有喇叭和麥克風，也不知道哪款 Android 的降噪會吃掉高頻；這張「手機型號 × 環境 × 錯誤率」表只能由人去量。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週用 spec 定協定，先做到兩台筆電互傳。第 2 週約同學實測 3–4 次，每次 1 小時，再調參。第 3 週做介面、PWA 離線、英文影片和說明頁，12/3 交。最可能扣分：ggwave 這類 data-over-sound 早就存在，說明頁要正面講差異（實測表、地震情境、完全離線）；評審在吵雜環境可能試不出來，必須附「同一台電腦開兩個分頁」的示範模式。

- **一句話**：Haunt Walk Kit — 一個「走到哪、手機就自動播那一段聲音」的瀏覽器語音導覽骨架，用它做出校園鬼故事夜遊、新生與行動不便者的無障礙導覽兩個 app（Skeleton Crew）
- **抄了誰**：直接抄第 1 名 InteractionKit 的形狀：骨架加兩個 app，再用 hook 讓別人繼續長新站點；也抄它「一個娛樂 app 配一個照顧人的 app」的組合。改的一點是把手勢追蹤換成 GPS 地理圍欄。
- **評分表怎麼拿分**：Impact：第二個 app 用聲音帶第一次來的人和行動不便者找系館、無障礙電梯和坡道，使用者是誰很明確。Tech：hook 在新增站點 JSON 時自動驗證圍欄半徑、音檔長度並重畫路線圖；steering 規定站點格式；spec 分成骨架和兩個 app；MCP 接 OpenStreetMap／Overpass 查步行路徑；PBT 驗證圍欄判定。Design：用印刷品式的站牌和地圖，夜遊版換成暗色紙質，同一骨架換兩層皮。Innovation：資料集是你親自錄的口述傳說，網路上沒有。Presentation：影片實地走一段，手機走到站點就自己響起。
- **AI 做不到的部分**：每條路線都要親自走。要在現場記 GPS 點和漂移範圍（樹下、大樓之間誤差常超過 20 公尺）來訂圍欄半徑；要請同學錄下他們真的聽過的校園傳說和學長姐的帶路口述；還要請一位行動不便的同學實際走一次，修正坡道和電梯路線。這些都得有人在現場。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週用純 JS PWA 做骨架（定位、圍欄、音訊佇列）。第 2 週挑兩個晚上走兩條路線並錄音。第 3 週給兩個 app 換皮、做模擬步行、錄影。最可能扣分：評審不在台灣，沒有「在地圖上拖小人模擬走路」的模式就等於打不開；錄音是中文，要配英文字幕；找不到真的行動不便測試者，Impact 的說法會變虛。

- **一句話**：Lantern Reader — 一個只有提燈照到的那幾行看得見的英文論文閱讀器，幫容易分心、英文非母語的大學生讀完一篇 paper（Costume Contest）
- **抄了誰**：抄 SpookBnB 的手電筒照明，把「恐怖逃脫」換成「專心閱讀」；排版抄 Seance 的陰森百科質感，但改成每天真的會用的工具。
- **評分表怎麼拿分**：Design：陰森就是功能。黑暗遮掉其他段落，燈跟著閱讀位置走，燈油燒完就提醒休息，再加上你擅長的印刷品式字級與行長。Impact：對象明確，用同學的實測數據撐住「有用」。Presentation：影片用同一篇 paper 做前後對比。Innovation：把遊戲的手電筒機制搬到閱讀上。Tech：spec 寫閱讀位置追蹤和無障礙需求；hook 在每次改 UI 時用 Playwright MCP 截圖並跑 axe 無障礙檢查；steering 寫排版規範（字級、行長、對比）。
- **AI 做不到的部分**：燈照幾行、亮度多少、燈油幾分鐘，只能靠真人測出來。找 12–20 位同學做組內對照：兩篇難度相近的 paper，一篇用一般頁面讀，一篇用 Lantern 讀，記錄讀完時間、理解小測驗分數和自評分心程度。AI 不能替真人讀，也生不出這份數據。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週用 arXiv 的 HTML 版當輸入（避開 PDF 雙欄解析），做燈光遮罩。第 2 週約兩場實測，每場 1 小時。第 3 週依數據調參，把結果圖放進說明頁，再錄影。最可能扣分：樣本小，n 要誠實寫；燈光對低視力讀者反而不利，要有關燈和高對比模式；若只看影片，評審可能覺得是噱頭，實測結果圖要放在影片前 60 秒。

- **一句話**：Crypt Ledger — 用 COBOL 跑複式記帳，把每一次 LLM 呼叫的 token 記成一本能跟帳單對上的帳簿，看清 AI 開發到底花了多少錢（Frankenstein）
- **抄了誰**：抄部落格獎 Dark Ledger「用 COBOL 驗算」的做法，把薪資換成 LLM token 帳；縫法抄 UnitSet，把 1959 年的 COBOL 批次、現代 LLM 用量紀錄和瀏覽器帳冊縫成一個 app。
- **評分表怎麼拿分**：Innovation：COBOL 批次結帳配 AI token，這個組合沒人縫過。Tech：用 PBT 證明「借貸永遠平衡」；hook 在每次 Kiro session 結束時自動記一筆分錄，所以這個作品自己的開發成本就是資料；steering 寫會計規則；自寫一個 MCP server，讓 Kiro 能問「這個 spec 花了多少」。Design：帳冊用印刷帳本的格線和鉛字感，月結像在地窖翻舊帳。Impact：對象是自費用 API key 開發的學生和獨立開發者。Presentation：影片最後揭露「做這個作品本身花了多少」。
- **AI 做不到的部分**：你過去幾個月真實的 token 紀錄，以及跟供應商實際帳單逐筆對出來的落差（cache 寫入與讀取、重試、計價改版）。AI 算得出一個數字，但不知道它跟你真正被扣的錢差多少；「對得上帳單」這層校正只能拿你自己的帳單做。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週讓 GnuCOBOL 跑在你的常駐主機上，定好分錄格式。第 2 週接 hooks、匯入舊紀錄、對帳。第 3 週做帳冊介面和影片，公開版用去識別化的資料。最可能扣分：評審會問「為什麼要 COBOL」，要講出「批次結帳加上帳不可改」的理由，不然像噱頭；使用者族群偏窄。另外要先確認 Kiro 能不能拿到逐次用量，拿不到就改記你其他的 API 呼叫。

- **一句話**：Dot Plan — 讓 1971 年的 finger 協定復活：每個 AI coding agent 做完事就更新自己的 .plan，你在終端機打 `finger` 或打開網頁，就知道它們昨晚做了什麼（Resurrection）
- **抄了誰**：抄 Faxi「舊協定加現代 AI」的 Resurrection 形狀，也抄 InteractionKit 用 hooks 自動接上新東西；把傳真換成 finger 和 .plan（Carmack 當年就用 .plan 寫開發日誌）。
- **評分表怎麼拿分**：Tech：這題本身就是 Kiro 的展示。agent hook 在任務完成或 spec 狀態改變時自動寫 .plan；steering 規定 .plan 的寫法；MCP server 讓不同 agent 互讀彼此的 .plan。Innovation：把 finger 拿來當多 agent 的狀態板。Impact：同時跑好幾個 agent 的開發者需要知道誰做了什麼。Design：網頁版做成等寬字的印刷日誌頁，agent 是「值夜班的幽靈」。Presentation：影片開場就是一行 `finger kiro@host`。
- **AI 做不到的部分**：一個在你常駐主機 79 port 上真的跑滿 23 天的 finger 服務，加上這段期間你自己的工作流（長期記憶、hooks、skills）實際產生的 .plan 紀錄。這是活的使用資料，AI 生不出來；哪些內容寫進 .plan 有用、哪些是噪音，也只有你真的用過才知道。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週用 Python 寫 finger daemon，加上網頁閘道，用免費子網域上線；之後每天開發這個作品本身就在產生資料。第 2 週做 MCP server 和多 agent。第 3 週做介面和影片。最可能扣分：評審覺得「這就是個 log 檢視器」，而且 Impact 只限開發者；對外開 79 port 要處理安全和濫用問題；如果 Design 不夠出色，會被當成純技術 demo。

- **一句話**：Broadsheet Kit — 在瀏覽器裡把內容排成「一張 A4 摺成 8 頁小冊」的列印骨架，用它做出社團的鬼故事 zine，和給長輩的大字用藥小冊兩個 app（Skeleton Crew）
- **抄了誰**：抄 Impulse Kit 的極簡（純 HTML/CSS/JS、說明頁短）和 InteractionKit「一個娛樂 app 配一個照顧人的 app」的組合；把手勢換成 CSS 列印拼版。
- **評分表怎麼拿分**：Design：你的印刷品味就是這題的主角，螢幕預覽跟印出來一模一樣。Impact：用藥小冊印出來能放進錢包，是長輩的真需求；社團則是你身邊真的會用的人。Tech：hook 在每次改版型時用 Playwright MCP 輸出 PDF 並檢查裁切線；PBT 驗證任意頁數的拼版順序都正確；spec 分成骨架和兩個 app。Innovation：瀏覽器直接做拼版（imposition），不需要排版軟體。Presentation：影片裡印一張、摺起來、剪一刀，就變成一本小冊。
- **AI 做不到的部分**：拼版到底對不對、留白會不會被不同印表機吃掉、中英混排的字級在紙上讀不讀得清楚，只能真的印出來、摺起來、拿給人看。要在學校和家用印表機各印一次並量邊界，再請 3–5 位同學家裡的長輩實際讀一次用藥小冊，依結果修正字級。
- **截止前怎麼做完，以及評審最可能扣分的地方**：第 1 週做拼版引擎和列印 CSS。第 2 週做兩個 app 的版型，實印並請長輩測試。第 3 週錄影、寫說明頁。最可能扣分：陰森感只在其中一個 app 裡；用藥內容有安全疑慮，要寫清楚「只排版、不給醫療建議」；評審在瀏覽器裡看不到紙，頁面和影片都要放實拍照片。
